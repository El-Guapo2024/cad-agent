# CLI CAD Agent Landscape 2026 — Verified Comparison vs. cad-agent v2

Research date: **2026-09-28**. All star counts, licenses, commit/contributor counts, and file citations below were pulled live from each project's own GitHub repository via the GitHub REST API (`gh api`, authenticated, so figures are exact counts, not estimates) and by reading primary source files directly (README, LICENSE, source, tests, CI config). Where a claim could not be confirmed from a primary source, it is marked **not found** rather than guessed. This note supersedes `closest_equivalents.md`, `comparison_table.md`, and `ai_cad_products_mcp.md` for every candidate it re-checks — those files were an earlier, unverified pass and contain several errors identified below.

**cad-agent v2 planned features (referenced throughout as F1–F10):**
F1 parametric Python parts on build123d · F2 agent-first CLI (subcommands, `--json`, pass/fail/unchecked exit codes, no MCP required) · F3 deterministic geometry gates (interference volume + clearance per pair, ray-cast wall thickness, in-plane web width, DFM per process) · F4 motion sweeps over axis travel · F5 tool/laser keep-out envelopes · F6 headless renders + visual regression vs. approved baselines · F7 bought-part STEP with provenance · F8 independent verifier (fresh rebuild, source hashing, spec.toml acceptance tests) · F9 eval set scored by the verifier · F10 parts library (rails, motors, extrusion, fasteners).

## 3. Key question: are the CADGenBench claims real and reproducible?

**Short answer: yes, CADGenBench is real, but the notes conflated two different, separately-published claims from two different projects, and only one of them ships reproducible evidence.**

- **CADGenBench itself is real and open.** Hosted leaderboard: `https://huggingface.co/spaces/HuggingAI4Engineering/CADGenBench`. Source repo: `github.com/huggingface/cadgenbench` — **136 stars, Apache-2.0, created 2026-05-27, last pushed 2026-08-07** (confirmed via `gh api repos/huggingface/cadgenbench`). Its own README describes two tasks (generation from an engineering drawing; editing an existing STEP given a change request), and its `docs/metrics.md` defines `cad_score` precisely: a hard validity gate (must be a watertight, meshable B-rep/BRep), then `cad_score = 0.4·shape_similarity + 0.4·interface_match + 0.2·topology_match` for generation tasks (editing tasks renormalize against the no-op input). It is tool-agnostic — any tool producing `output.step`/`output.stp` can submit.

- **Claim A — build123d-mcp's README** (`https://github.com/pzfreo/build123d-mcp`, lines 25–27): *"On the public CADGenBench leaderboard in June 2026, using build123d-mcp raised the same model's score from 0.360 to 0.457 and CAD validity from 88% to 100%."* This is real prose in the shipped README, so the earlier notes did not fabricate it. But: **no model name, no leaderboard permalink, no methodology file, and no raw trial data are provided in the repo** — a grep of the full 177-file source tree found no `benchmarks/` or evidence directory. The CHANGELOG does show CADGenBench used constantly as an *internal* regression-testing tool (e.g., "A CADGenBench sweep (`gpt55-v0368-xhigh-full`) caught it live: fixture 240...", "hit ~29/81 benchmark runs", references to a "cadgenbench-build123d field report") — real and detailed, but not a public evidence package, and a GitHub search for a `cadgenbench-build123d` repo returns nothing. **Verdict: the claim is genuine but not independently reproducible from what's published.**

- **Claim B — agentcad's own evidence package** (`benchmarks/cadgenbench/gpt-5-nano-2026-08/` inside `github.com/jdilla1277/agentcad`) is a **separate, much more rigorously documented** claim, with completely different numbers: comparing GPT-5 Nano with direct `build123d==0.10.0` access vs. GPT-5 Nano using `agentcad==0.4.1`'s CLI+skill, on 81 CADGenBench fixtures (49 generation + 32 editing):

  | Measure | Without agentcad | With agentcad | Change |
  |---|---:|---:|---:|
  | CAD Score | 0.124 | 0.184 | +48.4% |
  | Valid outputs | 27/81 | 67/81 | 2.48× |

  This ships `methodology.json` (exact harness/model revisions, SHA256 hashes of both submission zips), raw per-fixture `*-trials.jsonl`, a `checksums.sha256`, the full harness source for both conditions, and a `verify_evidence.py` script that recomputes the totals locally. Its own README is unusually candid about limits: *"This is one run per condition, not a statistical study... These results establish a useful directional result for this model and setup, not that the effect generalizes to every model."* **Verdict: real, reproducible, and self-limiting — the strongest-evidenced benchmark claim found in this entire survey.**

- These are **two different claims** (different metrics scale — 0.360–0.457 vs. 0.124–0.184 — different projects, different runs); neither prior note distinguished them, and neither number appears in the other project's repo.

## 4. Per-project deep dives

### 4.1 agentcad / AgentCAD — `github.com/jdilla1277/agentcad` (homepage `agentcad.dev`)

- **Facts**: 140★, 16 forks, 36 open issues, Apache-2.0 (LICENSE file + README both confirm), created 2026-06-02, pushed 2026-09-28 (today), 4 contributors (jdilla1277: 188 commits, dchaudhari7177: 7, pollychen-lab: 1 — i.e., one dominant maintainer), **197 commits** total, 12 tagged releases (v0.2.1 → **v0.6.0** current).
- **Kernel**: build123d by default; CadQuery available as an explicit, separately-installed (`pip install "agentcad[cadquery]"`) compatibility mode — confirmed in README.
- **CLI** (from README, `src/agentcad/commands/*.py`): `agentcad run script.py --label L [--preview] [--render iso,front] [--export stl,glb]`, `measure`, `check-spec output.step spec.json`, `inspect`, `parts list/show/view`, `diff 1 2`, `view old.step new.step`, `viewer [open|status|stop]`, `docs [section]`, plus `init`, `daemon`, `feedback`. Every command's final response is **structured JSON on stdout**, with human-readable progress on stderr — an explicit, documented convention matching F2's spirit.
- **Exit codes**: `check-spec` (and similar) use `exit_code=1` only for *command* errors (bad file, bad path) — a failed spec comparison still exits with `status: "success"` and the pass/fail lives only in the JSON body's `passed` field (`src/agentcad/commands/check_spec.py` lines 37–38, 58–98). So the CLI does **not** map spec pass/fail to the process exit code the way F2 wants; `run`'s `is_valid` field is tri-state (`True`/`False`/`None` for e.g. timeout), which is the closest analogue to a pass/fail/unchecked convention.
- **Spec/checklist**: `check-spec` compares measured **cylindrical features only** against a JSON checklist — narrower than a general spec format.
- **Interference/assembly**: `diff` computes real shared/reference-only/candidate-only solid volume, but between **two versions of the same build**, not pairwise across distinct parts in an assembly — confirmed by grepping the full 228-file tree (excluding the benchmark folder) for "interferen/assembly/keepout/dfm/wall": no hits.
- **Tests**: exceptionally large — 130+ files under `tests/` and `tests_b3d/`, including deliberately adversarial STEP/BREP fixtures (`bowtie_prism_invalid.brep`, `nonmanifold_edge_prism.step`, `touching_edge_solids.step`, `overlapping_members.step`) for validation/comparison logic.
- **Verdict: borrow heavily, don't adopt wholesale.** The JSON-stdout/stderr-split convention, the versioned build-directory model, and the checklist-comparison pattern are all directly reusable design ideas. It is missing DFM, keep-out, motion-sweep, cross-part interference, an independent (separate-process) verifier, visual regression, a maintained eval set, and a parts library — i.e., most of what differentiates cad-agent v2.

### 4.2 build123d-mcp — `github.com/pzfreo/build123d-mcp`

- **Facts**: 96★ (exact match to prior notes), 13 forks, 59 open issues, Apache-2.0, created 2026-04-30, pushed 2026-09-25, 10 contributors (pzfreo: 409 contributions — dominant single maintainer — plus `github-actions[bot]`: 86), **560 commits** (exact match to the prior notes' "560+"), 30 tagged releases (v0.3.61–v0.3.90).
- **What it is**: an MCP server ("Give your AI CAD eyes") for Claude/Cursor/VS Code/Cline/Codex CLI. `pyproject.toml` does declare `[project.scripts] build123d-mcp = "build123d_mcp.cli:main"`, so it **is** pip-installable as a shell command — but reading `cli.py` shows `main()` only parses server-configuration flags (`--transport stdio|http`, `--library`, sandboxing flags, `--experimental`, etc.) and then calls `server.mcp.run()`. There is no agent-facing one-shot subcommand like `build123d-mcp validate part.py --json`; the only non-server subcommand is `install-skill`. **It is not the F2-style standalone CLI** despite having a `[project.scripts]` entry.
- **Tool surface**: SPEC.md is explicitly marked "historical, not maintained... there are now 37 tools (not five)" and directs readers to `llms.md`/README instead. The real tool set (`src/build123d_mcp/tools/*.py`) includes `analyze_printability`, `align_check`, `cross_sections`, `design_audit`, `diff`, `find_features` (hole/boss/countersink pattern recognition), `mesh_analysis`, `render_drawing` (GD&T-aware engineering drawings), `verify_spec`, `bd_warehouse_resource` (introspects the installed `bd_warehouse` package into a browsable catalogue via `inspect.signature()`), and a library-loading system for custom part files.
- **verify_spec — an important design lesson for F8**: `tools/verify_spec.py`'s own docstring: *"Each requirement is tagged PASS / FAIL / UNVERIFIED... never claims the design is 'correct'."* It checks a JSON spec (`envelope_mm`, `volume_mm3`, `solid`, hole/boss/countersink features, `wall_thickness_at`/`material_at_point` probes, numeric parameter ranges) against the built part. **This is off by default** (`--experimental` flag required) because, per the CHANGELOG: *"Field data from two full CADGenBench sweeps showed fixtures that called `verify_spec`/`suggest_spec` scored worse on average... a `conforms: true` verdict appears to read to an autonomous agent as a stop signal, and the agent finalizes-and-exports even when its own prose has just named an unfixed fidelity gap."* This is direct evidence for cad-agent v2's own design choice to run the verifier as a **separate process from the generating agent** rather than exposing it as just another tool the same agent can call and then stop on.
- **Tests/CI**: real, large test suite (69 files under `tests/`), `.github/workflows/ci.yml` and `publish.yml`, `tests/conformance-baseline.yml`. Mature engineering practice: ADRs under `docs/adr/`, `CONTRIBUTING.md`, `security.md`.
- **Verdict: borrow ideas, don't adopt the architecture.** Best-in-class single-part validity/printability/feature-recognition tooling and the bd_warehouse-catalogue-introspection pattern are directly reusable; the MCP-first architecture and the verify_spec cautionary tale are the two biggest takeaways, not the tool to depend on for F2's CLI mandate.

### 4.3 text-to-cad — `github.com/earthtojake/text-to-cad` (homepage `texttocad.dev`)

*(verified via a delegated sub-agent using the same `gh api` primary-source method; citations are to actual repo files it fetched)*

- **Facts**: **16,461★**, 1,705 forks, 16 open issues, MIT (copyright "Thompson Labs LLC" per the actual `LICENSE` file), created 2026-04-22, pushed 2026-09-28 (today), 26 contributors, **1,389 commits**.
- **What it is**: a monorepo of agent-invokable **skills** (installable via `npx skills add earthtojake/text-to-cad` or as native Claude Code / Codex / Grok Build plugins), not a unified CLI binary. `packages/cadgen` (Python, build123d-based kernel), `packages/core` + `packages/ui` (JS runtime/viewer), `apps/web` + `apps/docs`. 13 skills: `cad`, `cad-viewer`, `step-parts`, `engineering-drawing`, `dxf`, `urdf`, `srdf`, `sdf`, `sendcutsend`, `dfam-check`, `dfm`, `gcode`, `bambu-labs`.
- **DFM/DfAM (F3d)**: `skills/dfm/SKILL.md` — measures draft, undercuts, and projected area from a mesh, reporting "measured evidence and the cited rule behind every finding" for sheet-metal/CNC/injection-molding. `skills/dfam-check` covers 3D-print wall thickness, overhangs, support volume, build orientation.
- **Parts library (F10)**: `skills/step-parts` — an off-the-shelf parts library (bearings, motors, screws, connectors); provenance model not independently confirmed.
- **Engineering drawings (F6a)**: `skills/engineering-drawing` produces dimensioned PDFs (views, hidden lines, hole callouts).
- **CI**: `.github/workflows/test.yml` runs a dependency-graph-driven multi-job suite (cadgen on Linux *and* Windows, core-js, web, skills, docs, packaging) — cross-platform rigor that is unusual among the projects surveyed.
- **No CLI, no eval set, no spec/acceptance-test format** were found.
- **Note on the star count**: the sub-agent that verified this judged the popularity "highly legitimate" given the CI rigor and concrete skill implementations it read; that judgment about *why* it is popular is inherently harder to verify than the code facts above, so treat the engineering substance (confirmed) as the load-bearing fact and the virality explanation as informed opinion, not a verified claim.
- **Verdict: borrow ideas, specifically the DFM/DfAM rule-citation pattern and the parts-library skill design.** It's a real, well-engineered, and (on code evidence) mature project, but architecturally it's a skills library requiring an agent host — it doesn't satisfy F2's "no MCP/host required" bare-CLI requirement any better than an MCP server does.

### 4.4 Multi-Agent-CAD ("MAC") — `github.com/Pan-Chera/Multi-Agent-CAD`

*(verified via delegated sub-agent, primary-sourced)*

- **Facts**: **1,009★**, 93 forks, 1 open issue, MIT (copyright Tsinghua University · IEI Lab, per LICENSE file), created 2026-07-30, pushed 2026-09-24, 2 contributors, 60 commits.
- **What it is**: a working Python framework + web UI, build123d-based, generating "editable CAD parts and multi-part assemblies from natural language." Entry points: `python -m multi_agent_cad.graph` (single part), `python -m multi_agent_cad.web` (REST API, `POST /api/run {"user_request": "..."}`), `python -m mac_assembly` (assemblies). Exports STEP/STL/GLB for parts, URDF for assemblies.
- **CLI/JSON**: no documented `--json` flag or subcommand exit-code convention; the web API accepts/returns JSON.
- **Verification**: CI has a two-stage design — "release-contract" (deterministic geometry checks, no external API calls) and "smoke-test" (full pipeline run, verifies STEP/STL artifacts) — a good small idea for cad-agent v2's own CI. Self-reported benchmark: "140/141 feature pass rate" on a 10-prompt internal evaluation vs. a "CAD Skills" baseline, and a 62.7× token-reduction claim; **no associated arXiv paper was found**, so this benchmark should be treated as vendor-reported, not independently published.
- **No DFM, no interference/clearance checks, no spec/acceptance format, no parts library** were found.
- **Verdict: skip as a component.** Popular and apparently legitimate (real CI, real code, not just paper artifacts), but feature-poor relative to cad-agent v2's plan; only the two-stage CI pattern is worth borrowing.

### 4.5 CADCLAW + MARB — `github.com/sunnyday-technologies/CADCLAW` and `.../MARB` (not in any prior note)

This project was missing entirely from the earlier research pass and is arguably the single closest match found anywhere in this survey for cad-agent v2's **verifier** half (F8/F9) — found via a broad re-search specifically because the prior notes' "nobody has a fresh-rebuild verifier" claim looked suspicious and warranted a fresh check.

- **Facts**: 19★, 1 fork, 0 open issues, MIT, created 2026-04-18, pushed 2026-09-10 (18 days stale as of this research), **1 contributor** (`nick-sunn3dcom`, 202/202 commits — solo project, bus factor 1). Has a Zenodo DOI (`10.5281/zenodo.19647390`) and a `CITATION.cff`, i.e., published as a citable software artifact. Real `tests/` suite (including actual NIST AP242 conformance STEP files, e.g. `nist_ftc_11_asme1_ap242-e2.stp`) and CI (`.github/workflows/tests.yml`).
- **What it does — and deliberately does not do**: its own README states plainly: *"CADCLAW does not generate geometry: no parametric plates, no bolt-circle helpers, no hole patterns. You draw the parts, CADCLAW seats them against each other and checks the result."* It **assembles** pre-authored STEP parts by a declarative `assembly_spec.v0.1` (YAML; parts placed by named connector-frame constraints, not hand-typed coordinates — "seat this connector frame against that parent frame") via CadQuery, then **verifies** the result through a chain of independent gates configured in `cadclaw.yaml`:

  | Gate | What it checks |
  |---|---|
  | Inventory | missing/extra parts by bbox signature |
  | **Interference** | solid-solid overlap via **BRep boolean intersection, not bbox** |
  | **Adjacency** | parts that should be near each other but aren't (e.g. "motor 600mm from mount") |
  | Dimensional | wrong thickness, swapped args, impossible dimensions |
  | Orientation | rotated/mis-faced parts vs. a declared expected face plane |
  | Floating | parts isolated beyond a max gap from structural labels |
  | Color/material | STEP AP242 metadata vs. expected |
  | PMI_PRESENT_SEMANTIC | presence of declared AP242 GD&T/datum classes |
  | ROUNDTRIP_STEP (opt-in) | AP242 import→export→reimport preservation |
  | **Structural** | beam deflection, motor torque budget, belt tension — explicitly *"static load math, not motion-clearance or full-travel sweeps"* (so **F4 is out of scope** by their own admission) |
  | **Tolerance** | worst-case, RSS, and Monte Carlo tolerance stacking with Cpk |
  | **Parity** | STEP-vs-STEP comparison, flags hidden/suppressed-part export drift |
  | BOM audit | BOM JSON vs. CAD assembly (qty, mfg_type, required/forbidden text terms) |
  | Render/Disassembly | STEP→PNG→animated exploded-view GIF via offscreen VTK |

  Every report carries a **confidence budget** (`checked` / `not_checked` / `assumptions`) and gates are separately version-stamped ("so method changes do not silently relabel historical results") — directly analogous to cad-agent v2's F8 "source hashing so stale results fail" instinct, applied to *methodology* versioning rather than source hashing specifically (no evidence of source-hash-based staleness detection was found).
- **CLI**: real, `pip install cadclaw`; commands include `cadclaw doctor` (environment check), `assemble validate-spec/build/check-round/inspect-component/render-views/render-sequence`, plus an "honesty toolchain" (`publish-audit`, `claim-audit` — a text linter for overclaiming in docs/BOMs). Also ships a local MCP server (24 tools) as an *option*, not a requirement.
- **MARB (Mechanical Assembly Readiness Benchmark)** — `github.com/sunnyday-technologies/MARB`, 1★, MIT, created 2026-05-30, pushed 2026-09-27 (yesterday). Its own description: *"Can AI assemble a real machine? One blind kit, one automated grader (CADCLAW), frontier and local models on one board. Grades, run registry, token ledger, and method — all open."* This is a genuine, if extremely new and small, **eval set of design tasks scored by an independent verifier** — precisely F9's shape.
- **Gaps vs. cad-agent v2**: no parametric generation (F1 doesn't apply — different scope by design), no motion sweep (F4, explicitly excluded), no keep-out envelopes (F5, not found), no ray-cast wall thickness or per-process DFM (F3c/F3d, not found — its checks are assembly-level, not single-part manufacturability), no visual-regression-against-baseline-pixels (its Parity gate is geometric STEP-vs-STEP, not rendered-image diffing).
- **Verdict: the strongest single "borrow ideas from" (and candidate for direct adoption of the verifier component) found in this entire investigation, scoped strictly to F8/F9.** It validates that cad-agent v2's central idea — a verifier that is architecturally separate from the generating agent, spec-driven, and paired with its own benchmark — is not just plausible but has already been built once, solo, and works. The bus factor (1 contributor, 19 stars) and narrow recency (last push 18 days before this research) are real risks for depending on it directly rather than just borrowing its design.

### 4.6 cad-khana — `github.com/cyberchitta/cad-khana`

- **Facts**: 16★ (exact match to prior notes), 0 forks, 0 open issues, Apache-2.0, created 2026-04-19, pushed 2026-09-27 (yesterday — very active), **1 contributor** (`restlessronin`, 147/147 commits), 147 commits, **0 tagged releases**, **no CI** (`.github/workflows` confirmed absent from the repo).
- **Real standalone CLI, not just a Claude Code skill**: `pyproject.toml` declares `[project.scripts] khana = "cad_khana.cli:main"` — installable and runnable as `khana` independent of any agent host (it *also* ships a Claude Code skill wrapper under `.claude/skills/` and `skills/cad-khana/SKILL.md`, but that is a convenience front-end, not the only way to invoke it). Confirmed subcommands (`skills/cad-khana/references/cli.md`): `khana check <target>`, `export`, `view`, `draw`, `run`, `diff <old> <new>`, `show <json-file>`, where `target` is `<module-path>[:<factory>]`.
- **Assertion DSL (closest match to F3a/F3b/F5 found anywhere)** — Python method calls on an `Assembly` object, recorded to `mechanism.json`: `assert_no_interference(a, b)`, `assert_interference(a, b)`, `assert_distance(a, b, min_mm=, max_mm=, along=)`, **`assert_clear_of(parts, keepout, ...)`** (a genuine keep-out-envelope primitive — F5), `assert_tangent_contact(a, b, tol_mm=)`, `assert_allowed_contact(a, b, max_overlap_mm3=)`, `assert_solid_count`, `assert_anchors_coincident`, plus group forms `assert_no_interference_between/within`.
- **Motion sweep (closest match to F4 found anywhere)**: `mechanism/sweep.py` — sampled multi-joint sweeps (a factory function `t -> Assembly`, not a single joint+range, explicitly because "a dump cycle drives several joints at once from non-linear schedules, which no single joint range can express"). For every sampled `t`, it bbox-prefilters candidate part pairs then computes exact **pairwise intersection volume** (`intersection_volume()`, using an `INTERFERENCE_VOLUME_EPSILON_MM3` threshold) for all remaining pairs, classifies each pair's contact as `always`/`never`/`transient` across the sweep, and can bisect to find the precise onset parameter of first contact to a given tolerance. The module's own docstrings are careful to flag that sampling is an inner approximation ("a pair reported `never` overlapped at none of the sampled parameters, which is not the same as never"). `Motion.over_joint(name, path, lo, hi, step)` + `khana check` then evaluates every declared assertion at the as-built pose *and* every sampled pose across the declared range.
- **Ray-cast wall thickness (F3c, real implementation)**: `printability/wall.py` casts rays inward from every tessellated facet's centroid (`_crossings`/`_ray`, using build123d's `find_intersection_points`), measures the span to the first valid exit, and reports a `WallSample` (thickness, entry/exit points, an "alignment" value that distinguishes a true parallel-face wall from a wedge tip). It separately handles concave creases/points (V-grooves, conical-pocket apices) via a dedicated fan-casting algorithm (`_crease_samples`) that naive facet-normal ray-casting would miss entirely. `min_wall(part)` returns the single thinnest reading.
- **Parts library**: no library of its own; bundles **bd_warehouse** as its standard-parts dependency (`skills/cad-khana/references/standard_parts.md` documents `fastener`, `bearing`, `thread`, `gear`, `sprocket`, `pipe`, `flange`, `open_builds`).
- **Verdict: adopt-or-closely-borrow, feature-for-feature the strongest match to cad-agent v2's F3/F4/F5 of anything surveyed**, despite being pre-1.0, single-maintainer, un-released, and CI-less. The interference/clearance/keep-out assertion vocabulary and the sampled-sweep-with-bisected-onset design are close enough to cad-agent v2's own plan that they are worth evaluating as a direct Apache-2.0 dependency, not just a design reference — with the bus-factor risk (1 contributor, 16 stars, 0 releases) weighed explicitly.

## 5. Key question: what does bd_warehouse actually contain, and does anything provide MGN rails / NEMA motors / extrusion for build123d or CadQuery?

**Source**: full source tree of `github.com/gumyr/bd_warehouse` (110★, Apache-2.0, created 2023-06-13, pushed 2026-09-21, 17 contributors, 262 commits) fetched and read directly.

- **Modules** (`src/bd_warehouse/`): `bearing.py` (deep-groove/angular-contact/cylindrical-roller/tapered-roller ball & roller bearings), `bushing.py`, `fastener.py` (screws/nuts/washers — ISO, DIN, imperial, heatset inserts, set screws — backed by ~30 parameter CSVs under `data/`), `flange.py` (ASME class 150–2500 flanges + drilling patterns, `data_flange/`), `gear.py` (spur/helical/rack/worm), `o_rings.py`, `pipe.py`, `retaining_ring.py` (DIN 471/472), `shaft_key.py`, `sprocket.py`, `thread.py` (ISO/Whitworth/BSPP/Acme/metric-trapezoidal/plastic-bottle ASTM D2911 & PCO1881), and **`open_builds.py`**.
- **`open_builds.py`** (Apache-2.0, by "Gumyr," dated 2024-06-27) parameterizes real **OpenBuilds** hardware and is the answer to the MGN/NEMA/extrusion question:
  - **`StepperMotor(motor_type: Literal["Nema17","Nema23","Nema23HighTorque"], motor_length=None)`** — a real, dimensioned parametric part (e.g. NEMA17: 48mm body, 5mm shaft, M3 mounting holes, per the class's own docstring table). **This directly refutes "✗ NEMA motors" in the prior comparison table.**
  - **`VSlotLinearRailProfile` / `VSlotLinearRail`** and **`CBeamLinearRailProfile` / `CBeamLinearRail`** — parametric **aluminum-extrusion profiles**, generated by `extrude()`-ing the profile sketch to a requested length. **This directly refutes "✗ extrusion" (the prior note's own hedge, "OpenBuilds parts only," undersold what OpenBuilds parts actually include).**
  - Also: `XtremeSolidVWheel` (V-wheel linear-motion bearings — a wheel-on-groove system, not a recirculating-ball rail), `CBeamGantryPlate`/`XLargeCBeamGantry`, `MetricLeadScrew`, `FlexibleCoupler` (explicitly sized for a 5mm NEMA17 shaft), `LockCollar`, `TNut`, `LBracket`, `RouterSpindleMount`.
- **The one part of the old claim that holds**: there is **no MGN-style linear guide rail** (the miniature recirculating-ball-bearing guide rail family — MGN12/MGN15 — common on 3D-printer gantries) anywhere in bd_warehouse. What it has instead is a *different*, also-real linear-motion technology: OpenBuilds' wheel-on-V-slot/C-beam-extrusion system. For cad-agent v2's specific MGN12/MGN15 requirement, this is a genuine, still-open gap.
- **cq_warehouse** (CadQuery's equivalent, `github.com/gumyr/cq_warehouse`, 152★, Apache-2.0) has **no such module** — its parts are `bearing.py`, `bushing.py`, `chain.py`, `drafting.py`, `extensions.py`, `fastener.py`, `sprocket.py`, `thread.py` (confirmed via directory listing) — no gears, no motors, no rails, no extrusion. It has also been **dormant since 2024-01-20** (2.7+ years) — effectively superseded by bd_warehouse under the same author.
- **FreeCAD Fasteners Workbench** (`shaise/FreeCAD_FastenersWB`, 420★, GPL-2.0, created 2015, pushed 2026-09-10, 45 contributors, 1,019 commits) is fasteners-only, FreeCAD-native (not build123d/CadQuery), and does not include motor/rail/extrusion families.
- **No other project was found**, in a dedicated fresh search, providing MGN-rail, generic 2020/2040 T-slot extrusion, or NEMA-motor parametric models for build123d or CadQuery beyond bd_warehouse's OpenBuilds module. `earthtojake/text-to-cad`'s `step-parts` skill claims an off-the-shelf parts library including motors, but its exact catalog/provenance model was not independently confirmed.

## 6. Key question: does build123d/OCCT expose minimum distance and interference volume?

**The prior notes' claim — "no kernel offers minimum distance between solids or interference volume" — is false.** Verified directly against build123d's source (pinned to release tag `v0.13.0`, current on PyPI) and OCCT's own reference documentation.

**Minimum distance** — `class Shape` in `src/build123d/topology/shape_core.py` (applies to any shape type, since `Shape` is the common base for Vertex/Edge/Wire/Face/Shell/Solid/Compound):
```python
# shape_core.py, distance_to (~L1446-1448)
def distance_to(self, other: Shape | VectorLike) -> float:
    """Minimal distance between two shapes"""
    return self.distance_to_with_closest_points(other)[0]

# shape_core.py, distance_to_with_closest_points (~L1450-1476)
def distance_to_with_closest_points(self, other: Shape | VectorLike) -> tuple[float, Vector, Vector]:
    """Minimal distance between two shapes and the points on each shape"""
    ...
    dist_calc = BRepExtrema_DistShapeShape()
    dist_calc.LoadS1(self.wrapped); dist_calc.LoadS2(other_wrapped)
    dist_calc.Perform()
    return dist_calc.Value(), Vector(dist_calc.PointOnShape1(1)), Vector(dist_calc.PointOnShape2(1))
```
Also present on the same class: `distance()` (one-shot float, ~L1434-1444) and `distances(*others)` (batch generator). Both `distance_to` and `distance_to_with_closest_points` are indexed in build123d's own API reference: `https://build123d.readthedocs.io/en/latest/direct_api_reference.html#topology.Shape.distance_to` (and `...distance_to_with_closest_points`).

**Underlying OCCT primitive, confirmed by direct import**, not inferred: `shape_core.py` line 104: `from OCP.BRepExtrema import BRepExtrema_DistShapeShape`. OCCT's own reference (`dev.opencascade.org` → redirects to `occt3d.com/dev/doc/refman/html/class_b_rep_extrema___dist_shape_shape.html`): *"This class provides tools to compute minimum distance between two Shapes (Compound, CompSolid, Solid, Shell, Face, Wire, Edge, Vertex)."* Caveat found in the same doc: interpenetration is reported via a separate `InnerSolution()` boolean ("...the other shape is completely or partially inside the solid"), **not** as a negative `Value()` — so "distance to closest point, or a same-class flag for full/partial containment" is the accurate description, not "negative distance for overlap."

**Interference volume** — a two-step, not one-call, process: `Shape.intersect(*shapes, tolerance=1e-6)` (and the `&` operator via `__and__`) return the overlap as a shape; for two solids this dispatches to `three_d.py`'s `_bool_op_list(..., BRepAlgoAPI_Common())` (import confirmed at `three_d.py` line 65: `from OCP.BRepAlgoAPI import BRepAlgoAPI_Common, BRepAlgoAPI_Cut`), and the resulting `Solid`/`Compound` exposes a `.volume` property (`three_d.py` ~L809-814, `compute_volume()`). So interference volume is `(a & b).volume` or `a.intersect(b)[0].volume` — **returns `None` if the shapes don't overlap at all**, not `0.0`. OCCT's own doc for `BRepAlgoAPI_Common` (same redirect pattern to occt3d.com): *"The class provides Boolean common operation between arguments and tools (Boolean Intersection)."*

**Practical conclusion for cad-agent v2**: both primitives cad-agent v2 needs already exist natively in build123d, requiring no custom OCCT bindings — `distance_to`/`distance_to_with_closest_points` for clearance, `(a & b).volume` for interference volume — confirmed against the current PyPI release (0.13.0).
