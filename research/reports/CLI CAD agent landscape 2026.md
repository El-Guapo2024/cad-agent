# Mapping the CLI CAD agent landscape

**Bottom line:** cad-agent v1 already matches or beats the external open-source field on most geometry checks — interference volume, clearance, ray-cast wall thickness, motion sweeps, tool/laser keep-out, visual regression against baselines, and bought-part provenance are all things v1's README already claims, and nothing found in this survey does all of them better. The gap v2 must close is architectural, not geometric: no project anywhere — including v1 — runs its checks as an independent process that rebuilds from source, hashes that source so stale results fail, and grades against declarative acceptance tests, paired with an eval set scored by that same verifier. The closest anyone has come is **CADCLAW + MARB** (MIT, solo-maintained, pushed within the last three weeks) for the verifier-plus-eval half, and **cad-khana** (Apache-2.0, solo-maintained) for the interference/clearance/keep-out/motion-sweep assertion vocabulary — both worth adopting or closely porting, with bus-factor risk weighed explicitly. **build123d** (Apache-2.0) already exposes the exact minimum-distance and interference-volume primitives v2 needs, natively, via OCCT — no custom kernel bindings required. **bd_warehouse** (Apache-2.0) already parametrizes NEMA17/23 motors and OpenBuilds V-slot/C-beam extrusion and rails, but nobody anywhere has a parametric MGN-style linear guide rail or generic 2020/2040 T-slot extrusion, so that piece has to be hand-built for the fab machine's gantry. Everything else surveyed — vendor MCP servers, proprietary AI-CAD copilots, most of the research literature — is reference material, not an adoption target, because it targets a different CAD host, is closed, or is MCP-shaped when the plan is CLI-first.

Legend: **n/v** = not verified in these notes (README/press claim only) · **n/d** = no date found in the notes. Facts marked "(verified)" were checked against primary sources (GitHub API, LICENSE files, source code) on 2026-09-28 in `closest_verified.md`; everything else comes from README/site text and is flagged accordingly. Where the two conflicted, the verified numbers below are the ones used.

The 2026 consensus across this literature is a four-tier verification hierarchy: execution errors (cheap, universal) → geometric metrics/Chamfer/IoU (proven RL reward) → VLM visual critique (catches asymmetries, blind to dimensions, modest ROI) → physics/FEA (gold standard, too slow for training loops, reserved for final acceptance). ## Where cad-agent v2 sits, and what to adopt, borrow, or skip

**The niche is architectural, and it's still open.** v1's README already claims interference volume + clearance via OCCT, ray-cast wall thickness, motion sweeps over declared axis travel, tool/laser keep-out envelopes, visual regression against approved baselines, and bought-part provenance with a VERIFIED flag. Cross-referencing that list against every project in Table 5 shows v1 already matches or exceeds the entire external field on five of those six (only cad-khana comes close, and only on interference/clearance/sweep/keep-out — nobody, anywhere, was found with visual regression against CAD renders or hash-tracked bought-part provenance outside v1 itself). What v1 does *not* have, and what nothing else surveyed has either, is a verifier that runs **out-of-process** from the generating agent, rebuilds from source, hashes that source so a stale result fails closed, and grades against a declarative `spec.toml`. That gap — not the geometry checks — is what v2 needs to build. It is also, not coincidentally, the exact failure mode build123d-mcp's own maintainer documented after two CADGenBench sweeps: exposing a verifier as *just another tool the same agent can call* let the agent read `conforms: true` as a stop signal and finalize past its own unfixed gaps. v1's 22 MCP tools are structurally that same pattern; v2's CLI-first, separate-process verifier is a direct fix, independently validated by someone else's field data.

### Adopt
- **build123d** as the kernel — Apache-2.0, and its `distance_to`/`distance_to_with_closest_points` and `(a & b).volume` primitives already cover the minimum-distance and interference-volume math v2 needs, confirmed against the current PyPI release. No custom OCCT bindings required.
- **bd_warehouse** as the parts-library base — Apache-2.0, actively maintained (pushed 2026-09-21), covers fasteners/bearings/gears/threads/flanges/pipes plus NEMA17/23 motors and OpenBuilds V-slot/C-beam extrusion and rails. Still need to hand-build a generic 2020/2040 T-slot extrusion profile and an MGN12/15-style linear rail — confirmed absent from every parts library surveyed.
- **Evaluate cad-khana's assertion/sweep/ray-cast-wall-thickness modules** for direct reuse or a close port: `assert_no_interference`, `assert_distance`, `assert_clear_of` (a genuine keep-out primitive), and `mechanism/sweep.py`'s sampled multi-joint sweep with bisected contact onset are the closest match to F3/F4/F5 found anywhere. Weigh this against its bus factor: one contributor, zero tagged releases, no CI.
- **Evaluate CADCLAW as the verifier component**, or its gate design as the blueprint for v2's own: MIT-licensed, real CLI, YAML spec format, version-stamped gates with confidence-budget reporting. Same caveat — solo-maintained, 19 stars, narrow scope (assembly verification only, no generation, no motion sweep by the author's own admission).

### Borrow (design ideas, not code dependencies)
- **agentcad**: the JSON-on-stdout / progress-on-stderr convention, the versioned build-directory model, and the checklist-comparison pattern for `check-spec`.
- **build123d-mcp**: the bd_warehouse-catalogue introspection trick (`inspect.signature()` over the installed package), its feature-recognition (hole/boss/countersink) and GD&T-aware drawing export, and — most importantly — the verify_spec postmortem as direct evidence for keeping v2's verifier a separate process.
- **CADCLAW**: the gate vocabulary itself (Interference / Adjacency / Dimensional / Orientation / Floating / Tolerance / Parity / BOM audit) as a starting taxonomy for spec.toml sections, and the confidence-budget report format (`checked` / `not_checked` / `assumptions`) so v2's verifier never silently overclaims. Its methodology-versioning (so a method change doesn't silently relabel old results) is the closest existing analogue to v2's source-hashing instinct, though nobody — including CADCLAW — does source-hash-based staleness detection; that stays a genuine v2 original.
- **text-to-cad**: the DFM/DfAM rule-citation pattern (report the measured evidence *and* the specific rule it violates), and the parts-library / engineering-drawing skill designs.
- **Multi-Agent-CAD**: the two-stage CI split (a fast deterministic "release-contract" stage plus a full "smoke test" stage) as a pattern for v2's own CI.
- **The research literature's four-tier verification hierarchy** (execution errors → geometric metrics → VLM critique → physics/FEA) as the blueprint for how v2's eval set should be scored, and **CADEngBench/MUSE's "looks like CAD, but does it work?" framing** as validation that v2's functional-requirements focus (envelope, keep-outs, bolt-hole interfaces, heat zones, mass/deflection budgets) targets a real, largely unsolved problem — only 8 of 300 frontier-LLM-generated designs reached FEA agreement on CADEngBench.

### Skip
- **openscad-agent** (no LICENSE file, 2 commits ever, dormant 8 months) and **ScadLM** (dormant 2+ years, author's own postmortem calls it a failure).
- **cq_warehouse** (dormant since 2024, superseded by bd_warehouse) and **FreeCAD Fasteners WB** (wrong kernel ecosystem — FreeCAD, not build123d/CadQuery).
- **Fornjot** (project concluded) and **Manifold as a primary kernel** (no STEP import/export, ruling out vendor-part workflows).
- **Zoo/KCL/Zookeeper**, **Blender MCP**, the **Fusion360/SolidWorks MCP servers**, and the vendor AI copilots (Onshape, SolidWorks AURA/Leo, Autodesk Bernini, nTop, CoLab, Leo AI) — proprietary, wrong CAD host, or not agent-callable. Per the explicit preference for CLI over MCP, none of the MCP servers are adoption targets regardless of maturity; they're read for UX and tool-surface ideas only.

## Conclusion

The most consequential finding here isn't a new tool — it's that the tool v1 already built is more capable than almost everything else in this survey, and the two projects that finally close part of the remaining gap (CADCLAW+MARB, cad-khana) surfaced only because the "nobody has a fresh-rebuild verifier" claim in the earlier notes looked suspicious enough to warrant a second search. Both are solo-maintained and barely three weeks old at the time of this research, which is a real adoption risk, but their existence answers the design question that matters most: an independent, spec-driven verifier paired with a small open eval set is buildable by one person in a few months, using exactly the OCCT primitives build123d already exposes. That reframes cad-agent v2's job from "invent a new verification paradigm" to "port a proven one, add source-hash staleness detection nobody else has, and point it at a fab-machine-specific eval set" — a materially smaller and more concrete scope than the landscape looked like before this research pass corrected the earlier notes' errors on licensing, star counts, and what agentcad and build123d-mcp actually do.
